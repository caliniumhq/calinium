# 404 Page

## Purpose

The 404 Page is Calinium’s calm missing-destination recovery page. It explains that the requested route is unavailable and gives the customer real routes back into the storefront without technical disclosure, fabricated content, forced redirects, or a dead end.

It owns missing-page recovery, a native search suggestion, a Homepage route, and an optional collections route. It does not own the missing content itself, automatic redirects, technical diagnostics, customer-account recovery, checkout, product/collection data, or a global error-monitoring system.

## Customer Goals

Customers should be able to:

- Understand that the requested destination is unavailable without being blamed or shown technical detail.
- Search the real storefront, return to the Homepage, and optionally browse a real collections destination.
- Retain ordinary Header and Footer navigation and leave the recovery page at any time.
- Use the page by keyboard, touch, screen reader, zoom, translated text, RTL layout, and reduced motion.
- Recover without an automatic redirect, fabricated substitute, trapped focus, or false claim that their intended content was found.

## Merchant Goals

Merchants should be able to:

- Keep broken-link recovery calm, branded, lightweight, and useful.
- Offer only genuine recovery routes that exist in the storefront.
- Enable or omit a collections link without creating a fake product or collection suggestion.
- Preserve platform routing boundaries and avoid exposing infrastructure, broken handles, customer data, or internal technical errors.
- Generate the same minimal safe recovery composition deterministically across resource-limited stores.

## Shopify Context

The 404 Page uses Shopify’s `404` template type. The current `apps/theme/templates/404.json` contains one active `main-404` section. Shopify owns the missing-route determination, 404 response behavior, routing, localized route context, search endpoint, root route, collections route, and any platform-level unavailable/restricted behavior.

The global Header, Footer, skip link, main landmark, cart drawer, predictive search, localization controls, and account entry remain global shell responsibilities. The 404 Page owns the customer-facing recovery hierarchy and does not diagnose why a route failed.

### Current implementation evidence

`apps/theme/sections/main-404.liquid` renders one localized H1, concise localized explanatory text, a server-rendered native search form to `routes.search_url`, and a root-route action. Its optional collections action uses `routes.collections_url` and is controlled by `show_collections_link`; color scheme is the other current setting. The form sends the real query parameter and a prefix option, then relies on Shopify’s Search Page route.

The current section has no automatic redirect, product/collection suggestion cards, browser-history manipulation, error code display, technical diagnosis, tracking/retry workflow, Contact Page link, or app-backed recovery. Its CSS preserves a calm centered reading region with a minimum height, a one-column search/action layout on narrow screens, and a responsive search row from the small desktop breakpoint.

The shared metadata implementation supplies canonical/title/optional description/Open Graph/Twitter output, but its current only explicit `noindex,follow` rule applies to Search. The current 404 source emits no dedicated robots meta tag and no structured data. This is an implementation gap; it must not be represented as an existing 404-specific indexing rule.

### Implementation audit

The baseline provides a safe, server-rendered recovery route: H1, explanatory text, real search, Homepage navigation, and optional Collections navigation. It appropriately avoids fabricated content and redirects. Future hardening requires an explicit verified 404 robots policy, locale-aware recovery review, optional feedback/support route only when real, and analytics/error monitoring ownership outside the page contract. No new recovery feature should weaken the present minimal path.

## Entry Conditions

Valid entry conditions include:

- A Shopify request for an unavailable storefront route.
- A stale internal or external link, mistyped URL, removed published destination, or unsupported localized path that Shopify resolves as not found.
- A Theme Editor preview of the 404 template.

The page must not assume which route the customer expected, whether content was deleted, whether a campaign link is stale, whether a customer is authenticated, or whether a replacement exists. It must not infer a product, collection, article, order, account, or route from the failed URL.

## Page Structure

The conceptual structure is:

```text
Global Header
        ↓
Main landmark
        ├── 404 H1 and concise factual explanation
        ├── Native storefront search recovery
        ├── Homepage route
        └── Optional genuine collections route
        ↓
Global Footer
```

The recovery path is intentionally compact. Search and navigation must remain more prominent than decorative artwork, promotion, or an explanation of technical failure.

## Required Regions

| Required role | Customer outcome | Rule |
| --- | --- | --- |
| Missing-page identity | Understand the current state. | One visible localized H1 identifies the unavailable destination without exposing error internals. |
| Concise explanation | Know what happened at a customer-meaningful level. | Explain that the page cannot be found or is unavailable; do not guess why. |
| Search recovery | Search real storefront content. | One native search form submits to Shopify Search and remains usable without JavaScript. |
| Homepage recovery | Return to a known route. | One real root-route link/action is always available. |
| Valid layout | Leave the page safely. | Global navigation, main landmark, stable controls, and Footer remain present. |

## Optional Regions

| Optional region | Use when | Omit when |
| --- | --- | --- |
| Collections route | The storefront has a meaningful accessible collections destination. | The merchant disables it or the route is not useful for the intended catalog. |
| Breadcrumbs | A truthful recovery trail helps customers understand a real prior hierarchy. | The missing route makes the hierarchy unknown or false. |
| Search suggestion | A verified native search query, correction, or shopper-entered query can be presented safely. | It would guess the missing destination or fabricate results. |
| Curated collection suggestion | A merchant-approved real collection gives a clearly labeled recovery route. | It assumes customer intent, has no approved collection, or looks like a replacement for missing content. |
| Contact/support link | A real public route is appropriate for broken-link reporting or assistance. | It promises support, exposes private contact details, or displaces direct recovery actions. |
| Restrained illustration | It supports calm orientation and does not delay recovery. | It is heavy, alarming, decorative noise, or the only communication of the state. |
| Newsletter | A separately approved, low-pressure subscription strategy exists. | It exploits a recovery state or treats error traffic as consent. |
| App Block or Custom Liquid | A reviewed recovery capability has real ownership, privacy/accessibility review, and fallback. | It adds automatic redirect, tracking, false suggestions, technical details, or client-only recovery. |

## Section Composition

The 404 Page remains recovery-first:

1. Localized 404 H1 and concise factual explanation.
2. One real native search recovery path.
3. One Homepage action.
4. Optional real Collections action.
5. Only then, an optional separately justified recovery support.

| Classification | 404 Page rule |
| --- | --- |
| Globally required | Header, Footer, skip link, and main landmark remain global. |
| Page-functionally required | One H1, factual explanation, native search, and Homepage route. |
| Recommended | Optional collections action when it is a useful real browse route. |
| Optional | Regions listed above, always subordinate to direct recovery. |
| Single-instance | H1, primary explanation, native search form, Homepage recovery, and primary recovery-action group. |
| Integration-dependent | Search suggestions, analytics, support, monitoring, app blocks, or any dynamic recovery feature. |
| Prohibited | Automatic redirect, fake results, fabricated missing-content substitute, technical error display, internal IDs, product/cart/checkout flow, forced newsletter, and unreviewed Custom Liquid. |

## Component Composition

| Component or family | 404 Page relationship |
| --- | --- |
| Error Page | Owns full-page failure communication; the 404 Page applies it to a verified missing destination. |
| Search Input, Field, Button | Compose one native Search recovery route. Search Page owns submitted result interpretation. |
| Text Link, Button, Breadcrumbs | Present real Homepage, Collections, and optional support navigation. |
| Empty State, Alert, Inline Message | Are not substitutes for a destination-level not-found state. |
| Responsive Image or Illustration | May support optional restrained context but cannot replace text or recovery controls. |
| Status Indicator | May communicate only a real transient recovery state; it must not invent availability. |

Components own local behavior and semantics. Shopify owns route failure and Search truth. The 404 Page owns calm recovery and refuses to guess what the customer intended to find.

## Content Rules

404 content is localized, concise, factual, and recovery-oriented.

- Do not name, display, infer, or recreate the missing product, collection, page, Article, customer account, order, or URL target.
- Do not expose stack traces, server names, request IDs, internal route data, Shopify configuration, customer data, debugging instructions, or unsupported technical explanations.
- Do not claim that the content was moved, deleted, temporarily unavailable, or will return unless the platform has supplied a verified state and a future implementation explicitly supports it.
- Do not fabricate search suggestions, collection cards, recent products, trends, support availability, discounts, popular routes, or recovery success.
- Keep the explanation calm and short. Avoid blame, urgency, all-caps warnings, panic-inducing illustrations, promotional copy, or pressure to subscribe.
- Homepage, Collections, and support labels must refer to real current routes. Search remains customer-entered and Shopify-resolved.

## Supported Variants

| Variant | Select when | Composition |
| --- | --- | --- |
| Minimal recovery | No verified supplemental recovery resource is necessary. | H1, explanation, native search, Homepage action. |
| Catalog recovery | The optional collections destination is real and useful. | Minimal recovery plus a clearly labeled Collections action. |
| Support-assisted recovery | A verified public support route adds value after direct recovery options. | Minimal/Catalog baseline plus one low-pressure support link. |
| Localized recovery | Shopify provides translated route and message context. | Same core composition with localized labels and route behavior. |

Variant selection is deterministic from route capability, merchant-approved public destinations, locale context, and actual integration availability. It must never be driven by a guess about the failed route or a desire to add promotional content.

## Supported States

| State | Required behavior |
| --- | --- |
| Not found | Render H1, factual explanation, native search, and root route. |
| Collections action enabled | Render the real collections action after core recovery controls. |
| Collections action disabled | Omit it cleanly; Homepage and Search remain available. |
| Empty or unusual search query | Submit safely to Shopify Search; Search Page owns results/no-results interpretation. |
| Optional support/collection suggestion unavailable | Omit it without replacing it with fabricated content. |
| Theme Editor preview | Expose the two current section settings and preserve the recovery structure. |
| Localized, RTL, zoom, or narrow viewport | Preserve readable text, labelled search, actions, and logical source order. |

The 404 Page has no successful “content recovered” state of its own. A customer reaches a new route only by choosing a real navigation or search action.

## Navigation and Actions

Native storefront search is the primary recovery operation. Homepage and optional Collections actions are primary navigation alternatives. Global Header and Footer routes remain available throughout.

Secondary actions may use a verified support link or a real public collection suggestion only after direct recovery. Links navigate; buttons submit the search form or operate an in-place control. Do not automatically redirect, change browser history, trap focus, intercept a back action, submit an empty search automatically, or make a promotional action look like recovery.

## Responsive Behaviour

The 404 Page is mobile first at 320 px, 375 px, tablet, desktop, wide desktop, browser zoom, large text, translated copy, and RTL.

- The explanation, labeled Search Input, submit action, Homepage link, and optional Collections link stay readable and touch-friendly.
- The current search form stacks at narrow widths and becomes a compact row only when width allows. Long translated labels wrap without clipping or horizontal scroll.
- Source order keeps the H1, explanation, search, and recovery actions in that order. Visual centering must not change keyboard/screen-reader order.
- Optional illustration or supplemental action never pushes the native search below the first practical recovery region.
- No recovery behavior depends on hover, motion, a pointer, or JavaScript.

## Accessibility

The 404 Page targets WCAG 2.2 AA:

- One main landmark, one localized H1, concise text explanation, visible or programmatically associated search label, and semantic `role="search"` form context.
- Keyboard-operable input and actions, visible focus, logical tab order, sufficient target size, and no automatic focus movement or traps.
- Missing-page status is communicated by text, not colour, icon, illustration, or motion alone.
- Search controls remain meaningful to screen readers; optional routes have distinct accessible names and do not use vague duplicated labels.
- Contrast, zoom, translated text, RTL, reduced motion, and no-JavaScript navigation all remain supported.
- Any future dynamic suggestion or alert uses restrained live-region behavior and must not repeatedly announce unchanged 404 content.

## SEO

An HTTP 404 response should not become a search destination. The intended SEO policy is `noindex` for 404 responses while preserving useful human recovery and normal internal links.

The current shared meta implementation does not emit an explicit 404 `noindex` directive; only Search currently receives `noindex,follow`. This page specification records the required future policy, not an existing implementation fact. Any implementation must coordinate response status, canonical behavior, merchant SEO policy, and platform behavior without indexing the missing route or creating a misleading canonical substitute.

Do not add headings, metadata, suggestions, or links intended to rank a missing destination. Do not claim a missing path is equivalent to Homepage, a collection, or an Article merely to consolidate SEO signals.

## Structured Data

The 404 Page emits no structured data in the current theme and should normally emit none. A missing destination is not a Product, Collection, Article, Search result, Offer, Review, Organization update, or FAQ.

Do not emit `WebPage`, `BreadcrumbList`, `ItemList`, Product, Collection, Article, Search, or error schema for the failed route unless a future verified technical policy establishes a meaningful, non-duplicative purpose. The default is omission rather than attempting to describe unavailable content.

## Shopify Settings

The current `main-404` settings are `show_collections_link` and color scheme. Shopify owns the missing route, root route, collections route, and Search route.

Future merchant settings may expose a verified public support route or a restrained illustration only through a dedicated, reviewed section contract. The design system controls error hierarchy, recovery order, labels, focus, contrast, spacing, breakpoints, motion, and noindex implementation boundary.

Do not expose arbitrary error copy, raw response code, route-target assumptions, redirects, search-result settings, internal diagnostic fields, animation speed, or fabricated collections/products in Theme Editor settings.

## Theme Editor Behaviour

The current `404.json` contains one `main-404` section. Theme Editor changes may toggle the real Collections action and choose a color scheme, but must preserve the H1, factual explanation, native search route, Homepage route, and absence of automatic redirect.

Any future optional section remains after the core recovery actions and must not replace the not-found semantics, invoke a client-only recovery path, reveal technical details, or create fake destination content. Section selection, reload, reorder, and setting refresh must not duplicate search handlers, focus behavior, or recovery controls.

## Performance Rules

- Server-render the H1, explanation, native Search form, Homepage link, optional Collections link, and global navigation. Recovery works without JavaScript.
- Keep the page small: no heavy media, app dependencies, product feeds, recommendation requests, client-side route lookup, or monitoring code is required for baseline recovery.
- Preserve stable geometry and immediate access to Search. An optional illustration or support integration must not become the LCP or delay controls.
- Do not poll, retry routes, preload unverified replacement content, automatically fetch recommendations, or install global listeners solely for 404 handling.
- Theme Editor lifecycle cleanup applies to any future enhancement; no duplicate form or controller behavior is permitted.

## AI Guidelines

AI should choose Minimal recovery by default and Catalog/support variants only from verified merchant-approved recovery routes. It should retain native Shopify Search, Homepage navigation, the optional actual Collections route, one H1, noindex intent, and the smallest sufficient composition.

AI must not infer the missing destination, create a replacement page, generate products/collections/Articles, invent technical causes, promise restoration, trigger redirects, add monitoring data, create fake search suggestions, or expose route/customer data. It must use documented components, preserve WCAG 2.2 AA and performance rules, and generate deterministically from identical approved inputs.

## Future Compatibility

Future work may harden 404-specific robots handling, locale-aware recovery, verified public support path, approved collection recovery, and observability ownership after platform and merchant-policy evidence exists.

Every refinement must preserve the core guarantee: no fabricated replacement, no automatic redirect, no technical disclosure, no customer trap, no commerce mutation, and one calm path back into the real storefront.
